title: Federated Credentials for Service Accounts

A federated credential lets a service account (a machine user) authenticate with a token that a foreign issuer signed,
for example a Kubernetes service account token, a CI system's OIDC token or another identity provider's token, instead
of with a key or secret the workload has to store. It is the receiving half of workload identity federation: the
credential names which issuer, which subject and which further claims may act as the service account.

A workload exchanges its foreign token for a short-lived machine token at the token endpoint (see
[Exchange a token](#exchange-a-token)); it stores no key and nothing to rotate.

## What a credential holds

| Field | Meaning |
| --- | --- |
| `issuer` | Compared exactly with the token's `iss` claim. An `https` URL with a host and without query, fragment or user information. |
| `key_source` | Where the verification keys come from: `issuer_metadata` (the issuer's OpenID Provider metadata at `{issuer}/.well-known/openid-configuration`, which must be reachable on a public address on port 443) or `pinned_keys` (a JSON Web Key Set stored on the credential). |
| `allowed_algorithms` | One or more of `ES256`, `RS256` and `EdDSA`. Anything else, `none` and the HMAC algorithms included, is refused. Pinned keys must fit them: RSA keys of at least 2048 bits for `RS256`, P-256 keys for `ES256`, Ed25519 keys for `EdDSA`, each with a unique `kid`, public keys only. |
| `audience` | The value the token's `aud` claim must contain. |
| `subject_rule` | A claim (for example `sub`) and either an `exact` value or a `pattern`. A pattern is an RE2 expression that must match the whole value and must begin with literal text, so `.*` and anything else that could match every subject is refused. Prefer a claim the issuer never reassigns, such as an immutable ID. |
| `claim_conditions` | Up to 20 further claims the token must carry with exactly the given string values, one condition per claim. |
| `max_token_age` | How long after its issue time (`iat`) a token is still accepted, even if it has not expired. More than 0, at most 24 hours. |
| `max_token_lifetime` | The longest lifetime of the machine token issued in exchange. More than 0, at most 1 hour. |
| `disabled` | A disabled credential is kept and listed, but accepts no token. |

The claims `iss`, `aud`, `exp`, `nbf`, `iat` and `jti` are checked by the exchange itself and cannot be used in a subject
rule or a condition.

## Permissions

Federated credentials have their own permissions, separate from `user.write`, which manages a service account's own keys:

- `user.federated_credential.read` to list them,
- `user.federated_credential.write` to add and update them, including disabling and enabling,
- `user.federated_credential.delete` to remove them.

By default only `IAM_OWNER` holds them. A user cannot manage its own federated credentials, and only machine users can
hold one.

## Manage credentials

The user service v2 offers four calls:

- `AddFederatedCredential` (`POST /v2/users/{user_id}/federated_credentials`) returns the new `credential_id`.
- `UpdateFederatedCredential` (`PATCH /v2/users/{user_id}/federated_credentials/{credential_id}`) changes only the fields
  sent; `disabled: true` disables the credential and `disabled: false` enables it again.
- `RemoveFederatedCredential` (`DELETE /v2/users/{user_id}/federated_credentials/{credential_id}`).
- `ListFederatedCredentials` (`POST /v2/users/{user_id}/federated_credentials/search`) lists a user's credentials,
  disabled ones included.

For example, to let a CI pipeline of one repository act as a service account:

```bash
curl -X POST "https://${CUSTOM_DOMAIN}/v2/users/${USER_ID}/federated_credentials" \
  -H "Authorization: Bearer ${TOKEN}" \
  -H "Content-Type: application/json" \
  -d '{
    "issuer": "https://token.actions.example.com",
    "keySource": {"issuerMetadata": {}},
    "allowedAlgorithms": ["RS256"],
    "audience": "https://'"${CUSTOM_DOMAIN}"'",
    "subjectRule": {"claim": "sub", "pattern": "repo:example-org/deploy:ref:refs/heads/main"},
    "claimConditions": [{"claim": "repository_owner_id", "value": "123456"}],
    "maxTokenAge": "600s",
    "maxTokenLifetime": "300s"
  }'
```

Every change is an event on the service account, recording who made it and which fields changed. Removing the service
account, its organization or the instance removes its federated credentials.

## Exchange a token

The workload sends its foreign token as the assertion of the JWT profile grant (RFC 7523), the grant a service account
also uses with a key of its own:

```bash
curl -X POST "https://${CUSTOM_DOMAIN}/oauth/v2/token" \
  -H "Content-Type: application/x-www-form-urlencoded" \
  --data-urlencode "grant_type=urn:ietf:params:oauth:grant-type:jwt-bearer" \
  --data-urlencode "scope=openid urn:zitadel:iam:org:project:id:${PROJECT_ID}:aud" \
  --data-urlencode "assertion=${WORKLOAD_TOKEN}"
```

The token's `iss` decides which path the request takes. When it is an `https` URL and at least one enabled credential
names exactly that issuer, the token is checked against those credentials. Any other assertion, including one signed with
a service account's own key, is handled as before.

A credential accepts the token when all of these hold:

- the token is signed with one of the credential's `allowed_algorithms` by a key of its key source, with a key type that
  fits the algorithm;
- `exp` is present and has not passed, `nbf` (if present) has passed, and `iat` is present, not in the future, and no
  older than `max_token_age`, even if the token has not expired yet. The server allows one minute of clock difference
  for `exp`, `nbf` and `iat`, but none for the maximum age;
- `aud` contains the credential's `audience`;
- the subject rule and every claim condition are satisfied.

With `issuer_metadata`, the keys come from the `jwks_uri` of the issuer's metadata, which must name the issuer exactly.
They are cached for 15 minutes. A token whose `kid` is not in the cache makes the server fetch the keys again (so a
rotated key is picked up), but not more than once a minute per issuer. If a fetch fails, keys older than 15 minutes are
not used and the exchange is refused. With `pinned_keys`, the issuer is never contacted.

When the credentials of more than one service account accept the same token, the exchange is refused: patterns cannot be
checked for overlap when they are written. Several credentials of one service account may accept it; the smallest
`max_token_lifetime` among them applies.

Each token is accepted once. It is identified by its `iss` and `jti`, or, without a `jti`, by its signed content (so
re-encoding the token or rewriting its signature does not make a new one). A second exchange of the same token fails on
every server of the deployment, for good.

The service account must be active and not locked, and its organization active, as for a key. The response is the one
the key-signed grant returns: the access token type, `client_id` (the service account's username), scopes and audience
are the same; the access token lives at most `max_token_lifetime` (or less, if the instance's access token lifetime is
shorter), and there is no refresh token: the workload exchanges a new token when the old one expires. The session's
authentication method is `federated_credential`: the token's introspection and an ID token carry it as `amr`, where a
key-signed session carries none.

Every exchange writes the event `user.machine.federated_credential_ixcans_fork.exchanged` on the service account, with
the `credentialId`, the token's `issuer`, `subject` (its `sub`), the `subjectClaim` and `subjectValue` the subject rule
matched, its `tokenId` (`jti`), the `assertionKey` that makes it single use, and the `oidcSessionId` of the issued
session. A JWT access token's `jti` begins with that session ID, so the token leads to the workload that obtained it.

A refused exchange returns `invalid_grant`, with one of these descriptions:

| Description | Cause |
| --- | --- |
| `assertion is not accepted by a federated credential` | No enabled credential of the issuer accepts the token. |
| `assertion matches the federated credentials of more than one machine user` | The token is ambiguous. |
| `assertion was already used` | The token was exchanged before. |
| `the machine user of the federated credential does not exist` | The service account was removed. |
